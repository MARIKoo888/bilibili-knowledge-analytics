## #1 mixin_key 算成了 64 位 → 接口一直 -403

- **现象**：签名函数跑通不报错，但请求返回 `{"code": -403}`，看不出问题在哪。
- **排查**：拿公开示例 key 对做断言，发现算出的 `mixin_key` 是 64 位（应为 32 位）。
- **原因**：B站混排表 `MIXIN_KEY_ENC_TAB` 有 64 项，但**要取混排结果的前 32 位**：`''.join(raw[i] for i in TABLE)[:32]`。漏掉 `[:32]` 时，MD5 的输入就完全错了。
- **解法**：`[:32]`；并用黄金值锁死（`ea1db124af3b7062474693fa704f4ff8`）。
- **教训**：**签名/加密类代码一定要有"黄金值断言"**，不要靠"跑起来没报错"判断正确。→ 面试可讲：如何验证一个没有参考输出的实现。

## #2 翻到第二页就被风控（-352 / -403）

- **现象**：第一页数据正常，第二页开始 `-352 请求过于频繁` 或 `-403`。
- **原因**：① 签名与参数一一绑定，`offset` 变了 `w_rid` 必须重算；② `wbi` key 有效期约 24h，硬编码第二天必挂；③ 频率过高触发风控。
- **解法**：每页重新签名；每次任务启动重新拉 `nav` 取 key；间隔 1.5s + 随机抖动；失败指数退避；必要时先访问首页拿基础 Cookie（否则 `-101`）。
- **教训**：反爬不是"能不能写出来"的问题，是"能不能稳定跑完"的问题 → 所以要有断点续爬和日志。

## #3 控制台中文乱码 & matplotlib 中文变方块

- **现象**：Windows 终端里中文输出成 `�����`；图表中文显示成方框。
- **原因**：控制台默认 GBK 编码；matplotlib 默认字体不含中文。
- **解法**：
  ```python
  import sys
  for _s in (sys.stdout, sys.stderr):      # 脚本开头强制 UTF-8
      try: _s.reconfigure(encoding="utf-8")
      except Exception: pass
  ```
  ```python
  import matplotlib
  matplotlib.rcParams["font.sans-serif"] = ["Microsoft YaHei"]   # 或 SimHei
  matplotlib.rcParams["axes.unicode_minus"] = False              # 负号不变方块
  ```
- **教训**：环境类问题会伪装成"代码问题"，先确认"是环境还是逻辑"。

## #4 搜索接口"成功"返回 0 条：`code=0` 但 data 里只有 `v_voucher`

- **现象**：签名算对了（`code=0 message=OK`），但 `data.result` 为空，拿到 0 条视频。看响应体才发现 `data` 里只有一个 `v_voucher` 字段。
- **原因**：`v_voucher` 是 B站**风控凭证**——没有设备 Cookie（`buvid3`）时，接口不报错，只回凭证。这是最容易误判"爬虫写好了"的坑：**状态码骗你，数据量不会骗你**。
- **解法**：先访问 `https://www.bilibili.com`，再调 `GET /x/frontend/finger/spi` 拿到 `data.b_3`（buvid3）/`b_4`（buvid4），用 `session.cookies.set("buvid3", b_3, domain=".bilibili.com")` 带上，然后搜索接口就正常返回 20 条。
- **教训**：**永远断言"拿到多少条"，而不是断言"没报错"**。爬虫脚本第一行日志应该是"本次取得 N 条"。

## #5 拿二级分区 id 当 `newlist` 的 rid 参数 → 静默返回空

- **现象**：想按细分分区取数，试了 201/124/228/207… 十几个 rid，全部 `code=0` 但没有数据，误以为"这些分区没内容"。
- **原因**：`newlist` / `ranking` 的 `rid` 参数只认**一级分区**（知识区 = 36）。二级分区 id 不是这样用的。
- **解法**：用一级分区拉一批内容，再读**每条视频自带的 `tid` / `tname`** 字段聚合出映射 → 实测得到知识区 8 个二级分区：228 人文历史、201 科学科普、208 校园学习、124 社科·法律·心理、207 财经商业、122 野生技能协会、229 设计·创意、209 职业职场。
- **教训**：接口文档没写清时，**先做探测再写采集**；把探测脚本留成工具（`reference/probe_endpoints.py --map-tids`），下次换分区不用重新摸索。

## #6 评论翻页被 -403 拒绝；`pn` 参数会给出"假的 is_end"

- **现象**：想按计划抓 2 万条评论。
  - `wbi/main?pn=1` / `pn=2` → `code=0`，但每次只回 **3 条**一级评论，且 `cursor.is_end=True`，而 `all_count=12454`。
  - 换成现代游标 `pagination_str={"offset":""}`（mode=2 或 3）→ 直接 **`code=-403`**。
  - 老接口 `/x/v2/reply?sort=0` → 0 条；`sort=2` → 3 条。
- **原因**：B站对**未登录**的评论列表做了限制，只给极少量"热门预览"；`pn` 是旧分页参数，接口收下但不生效，于是 `is_end` 谎报为 `True` —— 让人误以为"这视频只有 3 条评论"。真正的翻页要走 `pagination_str` 游标，而它对匿名请求返回 -403。
- **解法（本项目采用）**：**文本分析主数据源改为弹幕**。
  - `GET /x/v1/dm/list.so?oid=<cid>`（cid 来自视频详情/排行数据）→ **无需登录，实测单视频 360 条**；响应为 deflate 压缩的 XML，用 `zlib.decompress(body, -zlib.MAX_WBITS)` 解。
  - 评论降级为**辅助证据**：每视频取 3–20 条高赞预览 × 几百个视频 ≈ 几千条，用来对齐"高赞观点"。
  - 不推荐把个人 SESSDATA 写进 `.env`（账号风险 + 会过期 + 一旦误提交就泄露）。
- **教训**：① **接口的"成功"和"有用"是两件事**，一定要核对条数；② 计划里写"2 万条评论"之前，先在单个视频上验证上限——**先探测上限，再定分析范围**。
- **意外收获（面试可讲）**：弹幕是"观看中的即时反应"，评论是"看完后的观点"，两者对照分析（同样内容，即时情绪 vs 事后评价是否一致）比单看评论更有业务价值。

## #7 采集量上不去：搜索被限流、`newlist` 不翻页、`page_size>20` 静默返回 0

- **现象**：按"关键词搜索翻页"的思路采集，结果
  - 搜索 `page_size=50` → `code=0` 但 **0 条**（`page_size=20` 正常）。
  - 连续请求约 40 次后，搜索无论怎么打都只返回 `v_voucher`，**换新 session、换关键词都没用**（IP 级时间窗限流），要等十几分钟。
  - `newlist` 传 `pn=1/2/3/5/10/100`，返回的几乎是**同一页**（去重后只多出 1–2 条，总计约 23 条）。
- **原因**：匿名接口对"深翻页 + 高频请求"做了限制，而且**用静默方式表达**（`code=0` + 空数据 / 风控凭证），不是报错。文档里写的 `page_size` 上限也不可信。
- **解法（已写进技术方案第十节）**：改用**种子扩样**策略：
  1. `ranking/v2` 8 个分区取种子（95 条/分区，同时拿到 `owner.mid`）
  2. **主力**：`space/wbi/arc/search?mid=&ps=30&pn=N` 拉 UP 主投稿（实测可深翻页，单个 UP 投稿上万）
  3. **补长尾**：`archive/related?bvid=`（实测 40 条/视频）
  4. 搜索只作主题补充，间隔 ≥10s，被限流就跳过
  5. 全套加**退避阶梯（30/60/120s）+ 断点续爬 + "拿到多少条"日志**
- **教训**：**采集方案要按接口的真实可靠性设计，而不是按文档写**；限流是常态，脚本必须"跳过并继续"，而不是崩掉。另外——`code=0` 永远不等于"成功拿到数据"。
- **顺带发现**：搜索接口的健康检查值得做成工具（`probe_endpoints.py --search-check`），否则你会对着正确的代码调一整晚。
