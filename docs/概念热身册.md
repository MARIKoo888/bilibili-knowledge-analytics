## 第 1 节 · 均值 vs 中位数（做 Q1 前必看）

**一句话**：均值 = 所有人分蛋糕后每人拿多少；中位数 = 排队站中间那个人的蛋糕大小。

**为什么需要**：B站播放量是典型的"极端值长尾"——绝大多数视频几千播放，个别爆款几千万。

```
举例：7 条视频的播放量
  800, 1200, 1500, 2000, 3000, 5000, 2000000   ← 最后一个是爆款
  均值   = 287500   ← 被那一条爆款拉到 28 万
  中位数 = 2000     ← 站在正中间那条，真实反映"典型视频"
```

**结论**：均值告诉你"这个分区总共有多少播放"，中位数告诉你"**一条普通视频能拿多少播放**"。
做"这个选题值不值得做"的判断时，**必须看中位数**——否则你会得出"知识区平均播放 28 万，很好做"这种荒谬结论（实际一条普通视频只有 2000）。

**本项目用在哪**：Q1 的需求量、Q2 的因变量、第 7–9 周所有 SQL 的默认口径。

**动手练**：
```
给你 8 条视频的点赞数，求均值和中位数：
  10, 12, 15, 20, 22, 30, 45, 900

均值 = ?       中位数 = ?
差值说明了什么？
```
<details><summary>答案（先自己做）</summary>

均值 = (10+12+15+20+22+30+45+900)/8 = 1054/8 = **131.75**
中位数 = 第 4、5 个的平均 = (20+22)/2 = **21**
差 6 倍多 → 说明有极端值（那个 900），**中位数才代表"典型视频"**。
</details>

## 第 2 节 · 供需比（做 Q1 用）

**一句话**：供给 ÷ 需求。比值越高 = 越多人抢同一块蛋糕 = 越内卷。

**为什么需要**："这个选题好不好做"不能只看播放高不高——播放高可能只是因为**发的人少**（供给少），也可能因为**大家就是爱看**（需求高）。要分开看。

```
供给量 = 该细分方向下有多少条视频      ← "多少人在做"
需求量 = 该细分方向视频的播放中位数    ← "一条普通视频能拿多少播放"

供需比 = 供给量 ÷ 需求量
  比值高 → 一堆人在发，但每条都没量 → 供过于求（红海，别进）
  比值低 → 发的人少，但每条都有量   → 供不应求（机会，优先做）
```

**⚠️ 常见错误**：分子分母写反。记住口诀——"**谁多谁在上面**"，你要找的是"人多肉少"的方向。

**本项目用在哪**：Q1 的核心指标 → 第 9 周的供需热度矩阵 → 简历里那条"识别出 3 个供不应求方向"。

**动手练**：
```
方向 A：120 条视频，播放中位数 8000
方向 B： 25 条视频，播放中位数 30000

(a) 两个方向的供需比分别是多少？
(b) 你是运营，下周先做哪个方向？为什么？
```
<details><summary>答案（先自己做）</summary>

(a) A = 120/8000 = **0.015**；B = 25/30000 = **0.00083**
(b) 选 **B**。B 的供需比更低 = 供给少、需求高 = **供不应求**；A 是 120 个人在抢 8000 的量，红海。
> 注意：这只是简化版。真实分析还要**控制分区和 UP 主体量**（见第 3 节），否则 B 可能只是"恰好有 2 个大 UP 主在发"。
</details>

## 第 3 节 · 控制变量（做 Q2 用，**全项目最值钱的一节**）

**一句话**：要比较 A 对结果的影响，必须先保证**其他会造成差异的因素都一样**。

**为什么需要**——这是新手最容易翻车的地方：
```
现象：时长 >30 分钟的视频，播放量明显更高。
天真结论："做长视频更容易火！"

真相：做 30 分钟以上长视频的，大多是粉丝几十万的大 UP 主
      （小 UP 主不敢做长视频）。所以高播放来自"UP 主本来就火"，
      不是"视频长"。

→ 你比较的其实是"UP 主体量"，不是"时长"。这个混淆因素叫 confounder。
```

**怎么控制**（本项目的做法）：
1. **只在同一个分区内比较**（知识区和鬼畜区的播放不可比）
2. **把 UP 主粉丝量分档**：如 <1万 / 1–10万 / >10万，**在每一档内部**比较时长
3. 只有当"在同一粉丝档内，长视频依然更好"时，才能说时长有效

**面试怎么讲**（背下来）：
> "我比较时长对播放的影响时，控制了分区和 UP 主粉丝量分档——因为长视频的创作者往往本身粉丝基数大，不控制的话，我测的其实是 UP 主体量，不是时长。"

**本项目用在哪**：Q2 的"必须控制的变量"栏、第 8 周周六的归因实验、第 12 周的偏差章节。

**动手练**：
```
某分区数据：
  <1万粉 UP 主：短视频中位播放 3000，长视频中位播放 2800
  1-10万粉 UP 主：短视频中位播放 15000，长视频中位播放 14000
  未分档时整体：短视频中位播放 5000，长视频中位播放 12000

(a) 为什么"整体比较"会得出"长视频更好"？
(b) 分档后真实结论是什么？
(c) 这个例子里的混淆因素是什么？
```
<details><summary>答案（先自己做）</summary>

(a) 因为长视频大多由大粉丝 UP 主产出，把大 UP 主的高播放算到了"长视频"头上。
(b) **分档后每一档里，长视频都不如短视频** → 时长没有正效果，整体结论是假的。
(c) 混淆因素 = **UP 主粉丝量**。这就是为什么必须先分档。
</details>

## 第 4 节 · 口径与分母（做任务 3、Q2 用）

**一句话**：说一个指标，必须同时说清"分子是什么、分母是什么"。

**为什么需要**：同样叫"互动率"，除以播放和除以点赞，结论能完全相反。**口径不统一，两个部门的数就对不上。**

```
互动率 = (点赞 + 投币 + 收藏) / 播放
         ↑ 分子：算哪些互动？  ↑ 分母：除以谁？

为什么分母常用"播放"而不是"点赞"？
  → 播放是最大的曝光口径，覆盖最广，最稳定。
  → 但注意：播放是累计快照值，会一直涨，所以必须声明"数据截取时间"。

为什么知识区特别要看"收藏率"（收藏/播放）？
  → 收藏 = "这个我以后要用" = 有用性，这是知识类内容的核心价值。
```

**动手练**：
```
视频甲：播放 10万，点赞 5000，投币 1000，收藏 2000
视频乙：播放  1万，点赞 1200，投币  400，收藏  900

(a) 分别算两条的互动率（用上面口径）
(b) 哪条内容"质量"更高？如果只看点赞数你会选错吗？
```
<details><summary>答案（先自己做）</summary>

(a) 甲 = (5000+1000+2000)/100000 = **8.0%**；乙 = (1200+400+900)/10000 = **25.0%**
(b) **乙**的质量更高（互动率 25% vs 8%）。但甲的**绝对点赞数**（5000）远高于乙（1200）——只看点赞数会误判甲更好。这就是"必须看比率、不能只看绝对值"的原因。
</details>

## 第 5 节 · SQL 从零（10 分钟读懂中位数那串代码）

> 适用场景：你看到 `ROW_NUMBER() OVER (PARTITION BY ...)` 一脸懵的时候。

### 5.1 SQL 是什么

**一句话**：SQL 是"对一张表提问"的语言。你描述**想要什么**，不描述**怎么算**（和 C 正好相反）。

### 5.2 一条贯穿全节的例子

假设 `video` 表只有 6 行（真实表有 458 行，道理一样）：

| bvid | sub_zone | view_cnt | is_duration_outlier |
|---|---|---|---|
| A | 职业职场 | 100 | 0 |
| B | 职业职场 | 200 | 0 |
| C | 职业职场 | 9000 | **1**（考证合集） |
| D | 科学科普 | 300 | 0 |
| E | 科学科普 | 1000 | 0 |
| F | 科学科普 | 1200 | 0 |

### 5.3 五个基本零件（按执行顺序记）

```sql
SELECT   sub_zone, view_cnt      -- ④ 要哪些列
FROM     video                   -- ① 从哪张表
WHERE    is_duration_outlier = 0 -- ② 筛掉哪些行
GROUP BY sub_zone                -- ③ 怎么分组（可选）
ORDER BY view_cnt DESC           -- ⑤ 怎么排序
LIMIT    10;                     -- ⑥ 只要前几条
```

**执行顺序不是从上到下**：`FROM` → `WHERE` → `GROUP BY` → `SELECT` → `ORDER BY` → `LIMIT`。
（这条要知道，否则"为什么 WHERE 里不能用 SELECT 的别名"会永远想不通）

| 零件 | 干什么 | 用 C 类比 |
|---|---|---|
| `WHERE` | **过滤行**，只留下满足条件的 | `if (cond) { 保留 }` |
| `ORDER BY` | **排序**，`ASC` 升序（默认）/ `DESC` 降序 | `qsort()` |
| `GROUP BY` | **分组汇总**，每组变成一行 | 遍历时按 key 累加，最后只输出每组的汇总 |
| `LIMIT` | 只要前 N 行 | `break` |

### 5.4 `WHERE is_duration_outlier = 0` 是什么意思

`is_duration_outlier` 是**我们自己加的一列**（在 `sql/01_schema.sql` 里定义，`TINYINT DEFAULT 0`）：
- `0` = 正常视频
- `1` = 时长超过 3 小时，疑似**直播回放/考证课程合集**

所以 `WHERE is_duration_outlier = 0` = **"只要正常视频，把合集类剔除"**。

为什么必须剔：那种 100 多小时的合集会把"播放中位数"和"时长分析"彻底带偏。上例里 C 那条 9000 播放的合集，会让职业职场的均值从 150 变成 3100。

### 5.5 `FLOOR` / `CEIL` 是什么

**就是 C 的 `math.h` 里那两个函数，完全一样**：

| SQL | 作用 | 例子 |
|---|---|---|
| `FLOOR(x)` | **向下**取整 | `FLOOR(2.5) = 2` |
| `CEIL(x)` / `CEILING(x)` | **向上**取整 | `CEIL(2.5) = 3` |

`(cnt+1)/2` 当 cnt 是偶数时会算出 `.5`，所以要用 FLOOR/CEIL 各取一次，拿到中间那**两个**位置。

### 5.6 `OVER` / `PARTITION BY`：窗口函数（重点）

这是最容易懵的地方。**核心区别只有一句**：

> `GROUP BY` = **把多行压成一行**（丢细节）
> `OVER` = **保留所有行，只多算一列**（不丢细节）

对比同一个需求"每个分区有多少条视频"：

**(a) 用 GROUP BY** —— 行数变少：
```sql
SELECT sub_zone, COUNT(*) AS n
FROM video
GROUP BY sub_zone;
```
结果 2 行：
| sub_zone | n |
|---|---|
| 职业职场 | 3 |
| 科学科普 | 3 |

**(b) 用 OVER** —— 行数不变，多一列：
```sql
SELECT sub_zone, view_cnt,
       COUNT(*) OVER (PARTITION BY sub_zone) AS cnt
FROM video;
```
结果 6 行：
| sub_zone | view_cnt | cnt |
|---|---|---|
| 职业职场 | 100 | 3 |
| 职业职场 | 200 | 3 |
| 职业职场 | 9000 | 3 |
| 科学科普 | 300 | 3 |
| 科学科普 | 1000 | 3 |
| 科学科普 | 1200 | 3 |

**`PARTITION BY sub_zone` = "按 sub_zone 分区，在每个分区内部各自算"**。它就是"分组"，但**不合并行**。

`ROW_NUMBER() OVER (PARTITION BY sub_zone ORDER BY view_cnt)` = **在每个分区内部，按播放量从小到大排，给每行一个序号**（第 1 小、第 2 小…）。

> 类比 C：`GROUP BY` 像"统计完只打印每组的总数"；`OVER` 像"给每一行贴一个标签，把组内排名写回该行"。

### 5.7 现在回头看中位数那串

```sql
WITH r AS (                                  -- 先算好一张临时表 r
  SELECT sub_zone, view_cnt,
         ROW_NUMBER() OVER (PARTITION BY sub_zone ORDER BY view_cnt) AS rn,  -- 组内排名
         COUNT(*)     OVER (PARTITION BY sub_zone)                   AS cnt  -- 组内总数
  FROM video
)
SELECT sub_zone, AVG(view_cnt) AS median_view, MAX(cnt) AS n
FROM r
WHERE rn IN (FLOOR((cnt+1)/2), CEIL((cnt+1)/2))   -- 只留"正中间"那 1 或 2 行
GROUP BY sub_zone
ORDER BY median_view DESC;
```

**拆成三句人话**：
1. `WITH r AS (...)`：先建一张临时表，每行都带上"我在组内排第几（rn）"和"我这组共几条（cnt）"
2. `WHERE rn IN (...)`:只保留正中间那 1~2 行
3. `AVG(view_cnt)`:把这 1~2 行取平均 = **中位数**

**为什么不能用 GROUP BY 直接算中位数？** 因为 `GROUP BY` 会把明细行压掉，你再也找不到"第 3 小的是谁"。**中位数需要"知道每行排第几"，所以必须用 OVER。** 这就是 MySQL 没有 `MEDIAN()` 却能用窗口函数算出来的原因。

### 5.8 动手练

用 5.2 那张 6 行小表（记住 C 是异常值，`WHERE` 会剔掉它）：

```
(a) 不加 WHERE 时，职业职场和科学科普各自的播放中位数是多少？200和1000
(b) 加 WHERE is_duration_outlier = 0 之后，职业职场的中位数是多少？150
(c) 均值分别怎么变？说明什么问题？
```
<details><summary>答案（先自己做）</summary>

(a) 不加 WHERE：
- 职业职场 3 条 = 100, 200, 9000 → 中位数 **200**（rn=2）；均值 (100+200+9000)/3 = 3100
- 科学科普 3 条 = 300, 1000, 1200 → 中位数 **1000**；均值 833

(b) 加 WHERE 后职业职场只剩 2 条 = 100, 200 → 中位数 = (100+200)/2 = **150**

(c) 职业职场均值 3100 → 150，**差 20 倍**。那个 9000 的考证合集一条就把均值毁了，但中位数只从 200 掉到 150（影响小）。
→ 结论：**均值怕异常值，中位数不怕。** 这就是"内容平台必须看中位数"的原因，也是你 Q1 用中位数不用总播放的实证。
</details>
